[[role-my-roles]]
=== 내 칭호 목록 조회

로그인한 회원이 보유한 칭호 전체를 조회합니다.

* *인증 필요*: 토큰이 없거나 유효하지 않으면(만료 포함) 401 `AU201` (<<overview-error-response,공통 에러>> 참고)
* 페이지네이션 없이 보유 칭호 전체를 한 번에 반환합니다. 보유 칭호가 없으면 `data` 는 빈 배열입니다.
* 정렬 순서는 보장되지 않습니다. 순서가 필요하면 클라이언트에서 `earnedAt` 등으로 정렬하세요.
* `data[].id` 는 보유 칭호 ID(회원-칭호 매핑 ID)이고 `data[].role.id` 는 칭호 ID 입니다. <<role-change-representative,대표 칭호 변경>>의 `memberRoleId` 에는 `data[].id` 를 사용합니다.
* `isRepresentative` 가 `true` 인 칭호는 최대 1개이며, 대표 칭호가 없는 회원은 모두 `false` 입니다.
* <<role-new-roles,새로 획득한 칭호 조회>>로 확인 처리된 칭호도 계속 포함됩니다. 한 번 획득한 칭호는 회수되지 않습니다.

[[role-roles]]
=== 전체 칭호 목록 조회

서비스에 등록된 모든 칭호(미획득 칭호 포함)를 조회합니다. 칭호 도감처럼 전체 칭호를 보여주는 화면에서 사용합니다.

* *인증 필요*: 응답은 회원과 관계없이 같지만, 토큰이 없거나 유효하지 않으면(만료 포함) 401 `AU201` (<<overview-error-response,공통 에러>> 참고)
* 페이지네이션 없이 전체 목록을 반환하며 정렬 순서는 보장되지 않습니다.
* 획득 여부는 이 API의 `data[].id` 와 <<role-my-roles,내 칭호 목록 조회>>의 `data[].role.id` 를 비교해 판단합니다.
* 자동 부여 칭호의 `description` 에는 획득 조건 안내 문구(예: `게시글 1회 업로드`)가 들어 있습니다. 운영자가 등록한 칭호는 임의 문구이거나 `null` 일 수 있습니다.
* 클라이언트가 칭호 획득을 직접 요청하는 API는 없습니다. 칭호는 활동에 따라 서버가 자동으로 부여하거나 운영자가 부여합니다. <<role-new-roles,새로 획득한 칭호 조회>>의 자동 부여 기준 표에 없는 칭호는 운영자만 부여할 수 있습니다.

operation::role/roles/200[snippets='http-request,request-headers,http-response,response-fields']

[[role-new-roles]]
=== 새로 획득한 칭호 조회

아직 사용자에게 노출되지 않은 신규 획득 칭호를 획득 순(오래된 순)으로 조회합니다. 칭호 획득 연출을 띄우는 용도입니다.

* *인증 필요*: 토큰이 없거나 유효하지 않으면(만료 포함) 401 `AU201` (<<overview-error-response,공통 에러>> 참고)
* *조회 즉시 확인 처리*: GET 이지만 상태가 바뀝니다. 응답에 담긴 칭호는 확인 처리되어 이후 호출에서 다시 반환되지 않습니다. 응답을 받으면 바로 획득 연출을 띄우고, 프리페치 용도로는 호출하지 마세요. 확인 처리된 칭호도 <<role-my-roles,내 칭호 목록 조회>>에는 계속 포함됩니다.
* 새로 획득한 칭호가 없으면 `data` 는 빈 배열입니다.
* *비동기 부여*: 자동 칭호는 활동 API의 처리(트랜잭션 커밋)가 끝난 뒤 별도 스레드에서 부여됩니다. 활동 API 응답 직후에 바로 호출하면 아직 반환되지 않을 수 있으므로, 화면 진입 시나 활동 후 약간의 지연을 두고 호출하세요.
* *자동 대표 지정*: 대표 칭호가 없는 회원이 칭호를 처음 획득하면 그 칭호가 자동으로 대표 칭호가 되며, 이때 해당 칭호의 `isRepresentative` 가 `true` 로 반환됩니다.
* 운영자가 부여한 칭호도 같은 방식으로 반환됩니다.

[[role-change-representative]]
=== 대표 칭호 변경

보유한 칭호 중 하나를 대표 칭호로 지정합니다.

* *인증 필요*: 토큰이 없거나 유효하지 않으면(만료 포함) 401 `AU201` (<<overview-error-response,공통 에러>> 참고)
* 경로의 `memberRoleId` 에는 <<role-my-roles,내 칭호 목록 조회>> 응답의 `data[].id`(보유 칭호 ID)를 넣습니다. `data[].role.id`(칭호 ID)가 아닙니다. 칭호 ID를 잘못 넣으면 아래 에러가 나거나, 그 값이 우연히 자신의 다른 보유 칭호 ID와 같으면 의도하지 않은 칭호가 대표로 지정됩니다.
* 이미 대표인 칭호를 다시 지정해도 200 으로 성공합니다. 대표 칭호를 해제하는 기능은 없습니다.
* 응답 `data` 는 항상 빈 객체 `{}` 입니다. 변경 결과가 필요하면 내 칭호 목록 조회를 다시 호출해 `isRepresentative` 를 갱신하세요.
* 변경된 대표 칭호는 회원 프로필의 `role`, 피드 작성자의 `author.role`, 하루 덕담 댓글·답글의 `role` 에 반영됩니다. 피드 댓글 작성자 정보에는 칭호가 포함되지 않습니다.
* `memberRoleId` 에 숫자가 아닌 값을 보내면 400 `C106` (<<overview-error-response,공통 에러>> 참고)
